# 方案：从"被动跟随"到"可自愈"，以及官方工具定义漂移

对应 `docs/architecture-and-limits.md` 局限 #5（全是被动跟随）和 #8（官方工具定义会漂移）。

---

## 一、先把问题拆准

现在网关里有 **7 类"抓包事实"**，写死程度各不相同：

| # | 事实 | 位置 | 现在能更新吗 | 上游变了会怎样 |
|---|---|---|---|---|
| 1 | TLS ClientHello | `bun_hello.go` 常量 | 要改代码重编译 | 全灭 |
| 2 | 头序/头值 | `bun_wire.go` 常量 | 要改代码 | 全灭 |
| 3 | 官方 system prompt | `tools/opencode_prompt_v2.txt` embed | 换文件重编译 | 全灭或降质 |
| 4 | 官方工具定义 | `tools/opencode_tools*.json` embed | 换文件重编译 | **降质**（见 T3） |
| 5 | 工具名前缀 | `mcp_`，env 可覆盖 | 改 env + 重启 | 全灭 |
| 6 | 描述黑名单 | `bannedDescriptionPhrases` 常量 | 要改代码 | **全灭**（实测） |
| 7 | UA 版本 | npm 拉 latest | **自动** | 无感 |

关键观察：**第 7 项已经自愈了**，而且它是唯一自愈的一项——因为它有"外部权威源 + 启动时同步"。
其余 6 项缺的不是检测能力，而是**"权威源"和"可替换的载体"**。

所以方案的核心不是"加智能"，是把这 6 项从"编译期常量"变成"可替换资产 + 有权威源可同步 + 失败时能定位到哪一层"。

---

## 二、问题一方案：资产化 + 诊断梯 + 定点轮换

### S1 资产化（前置条件，别的方案都依赖它）

把 1–6 搬到 `assets/`，运行时优先读文件，读不到回退 embed：

```
assets/
  tls_hello.json        # cipher/扩展顺序/groups/ALPN/版本
  headers.json          # 头名、头序、头值模板
  prompt.txt            # 官方 system prompt
  official_tools.json   # {"cli_version","captured_at","tools":{name:{description,parameters}}}
  tool_policy.json      # {"prefix":"mcp_","desc_mode":"blacklist|digest|neutral"}
```

加载优先级：`ZEN_ASSET_DIR/<name>` > `go:embed` 默认值。

**没有这一步，任何"自愈"都得改代码发版**——那就还是被动跟随。

- 工作量：中等（2–3 天）
- 风险：低（纯搬运，有默认值兜底）
- 收益：上游变化 = 换文件 + 重启，不发版

### S2 诊断梯（自愈的"定位"环节）

有 429 时（或每 30 分钟）按顺序跑 5 发，每发只比上一发多改一个维度：

| 步 | 载荷 | 通过意味着 | 失败意味着 |
|---|---|---|---|
| 0 | plain，无工具 | 出口/额度健康 | **出口死了 → 直接退出，不轮换** |
| 1 | plain + 完整官方工具集 | 官方集仍被接受 | 官方定义漂移 → 换 `official_tools.json` |
| 2 | plain + 第三方工具 + 中性描述 | 改名路径可用 | 前缀被学 → 轮换 prefix |
| 3 | plain + 真实 DSH 描述 | 描述黑名单够用 | 黑名单有漏 → 收紧 desc 策略 |
| 4 | 官方名子集 + 真实参数 + 中性描述 | 参数级安全 | 需要参数级脱敏 |

**第 0 步不通过就必须终止判断**——这是 v0.9.36 那次误判（拿出口已死的样本得出"描述不重要"）固化成代码的教训。

- 工作量：中等（2 天）
- 风险：每轮最多 5 发；必须节流（只在失败率超阈值时触发，不是常驻）
- 收益：把"感觉不对"变成"第 3 层坏了"

### S3 定点轮换（自愈的"执行"环节）

每个维度一个候选池，由 S2 的结果决定只换哪一层：

| 维度 | 候选池 | 触发条件 |
|---|---|---|
| prefix | `mcp_` → `mcp__srv__` → `tool_` → `fn_` | S2 第 2 步失败 |
| desc 策略 | blacklist → digest（首句摘要）→ neutral | S2 第 3 步失败 |
| prompt | 当前版 → 上一版 | S2 第 0/1 步通过但全量仍 429 |
| tools 资产 | 当前 → 新抓包 | S2 第 1 步失败 |
| UA | 已自动 | — |

状态落盘 `state/rotation.json`，重启保留；每层带"上次切换时间"，避免抖动。

- 工作量：中等（1 天，依赖 S2）
- 风险：**频繁换形态本身就是异常信号**。所以规则是"只换坏的那一层，换完必须复测，不通过则回滚"
- 收益：从"等人来修"变成"自己试下一档"

### S4 定时重抓流水线（权威源）

这个**已经建了 80%**。`zen-direct-v2/.github/workflows/capture-cli-vs-gateway.yml` 现在就在做：

```
npm install -g @opencode/cli@latest
python3 tools/capture_proxy.py --port 19100 --out captures
（CLI 与网关都指向本地 sink）
→ 从捕获 body 里 dump tools
```

缺的只是后半段：

1. 把捕获到的 `tools[]` 归一化成 `official_tools.json`（`name → {description, parameters}`）
2. 与仓库版本逐字段 diff
3. 有差异 → 提交 + 开 PR（或推 main 打 tag）
4. 无差异 → 什么都不做
5. 同一趟顺带产出：CLI 版本号、prompt 全文、header 集合、ClientHello 的 JA4

调度：每天一次 cron，1 个 runner × 约 3 分钟。

- 工作量：小（1 天，主要工作在归一化和 diff）
- 风险：低
- 收益：6 个资产有同一条权威源

### S5 漂移告警（不发版也能发现）

`/health` 增加：

```json
"assets": {
  "prompt": {"sha": "a1b2c3d4", "captured": "2026-11-17"},
  "tools":  {"sha": "e5f6a7b8", "cli_version": "2.3.0"},
  "hello":  {"ja4": "t13d1713h1"},
  "policy": {"prefix": "mcp_", "desc_mode": "blacklist"}
}
```

外部监控一比对就知道哪个资产过期了。

- 工作量：小（半天）
- 收益：把"上线后才知道坏了"提前到"监控里能看到"

## 三、问题二方案：官方工具定义漂移

### 现状

`stubs.go` embed `opencode_tools_2_2.json`；`renderOfficialTool` 命中就用真定义，缺失回退 `"Agent tool <name>"` + 空 schema。

### T1 自动重抓 + 资产化

复用 S4 + S1：`opencode_tools_2_2.json` → `assets/official_tools.json`，带版本与抓取时间。抓到新版就替换，重启生效，不发版。

- 工作量：随 S1/S4，不额外增加

### T2 用"官方集是否仍被接受"做漂移探针

S2 第 1 步就是它。官方集被拒 → 要么 schema 变了，要么名字集合变了 → 触发 S4 重抓 + 告警。

- 工作量：随 S2

### T3 宽松兜底：把硬失败降级成软降级（**优先级最高**）

2026-11-17 第三轮实测（24 个出口 IP）：

| 形态 | 结果 |
|---|---|
| 14 个官方名 + 中性描述（`"Tool read."`）+ 通用参数 | **4/4 200** |
| 13 个官方名（同上） | 4/4 200 |
| 4 / 2 / 1 个官方名（同上） | 全 200 |

**说明上游校验的核心是"名字集合"，schema 文本不是硬要求。**

所以定义缺失/过期时不需要硬失败，改成三档降级：

1. 命中真定义 → 用真定义（模型文档最好）
2. 未命中 → 中性描述 + 保守 schema（**已知能过**）
3. 永不因为"没有定义"而让整个请求失败

这把"漂移"从**可用性问题**降成**质量损失问题**——最坏情况是模型对某个工具的理解变差，而不是全站 429。

- 工作量：小（1 小时，`renderOfficialTool` 的 fallback 从 `"Agent tool X"` + 空 schema 改成中性描述 + 保守 schema）
- 风险：低（有实测支撑）
- 收益：**单项最高**

### T4 不要做的事

- **不要写"描述文本分类器"**判断一段描述是不是 DSH 指纹。这类判别不可靠，误杀会毁掉模型对工具的理解；黑名单 + 宽松兜底组合更稳。
- **不要为了追 schema 每天发版**。资产化之后这条就解耦了，发版只发逻辑。
- **不要在没有出口健康对照的情况下调整任何指纹策略**（v0.9.36 的教训）。

## 四、优先级与工作量

| 顺序 | 项 | 工作量 | 风险 | 解决什么 |
|---|---|---|---|---|
| 1 | **T3 宽松兜底** | 1 小时 | 低 | 定义漂移从"全灭"降为"降质" |
| 2 | S5 资产版本上报 | 半天 | 低 | 漂移可见 |
| 3 | S1 资产化 | 2–3 天 | 低 | 一切自愈的前置条件 |
| 4 | S4 定时重抓 | 1 天 | 低 | 6 个资产有权威源 |
| 5 | S2 诊断梯 | 2 天 | 中 | 失败可定位到层 |
| 6 | S3 定点轮换 | 1 天 | 中 | 自动试下一档 |

**S2/S3 必须最后做**，因为它们要"轮换"的目标得先由 S1/S4 提供；在资产还写死在代码里的时候做轮换，等于让代码自己改代码。

## 五、做完之后能达到什么程度

| 上游变化 | 现在 | 做完后 |
|---|---|---|
| 抬 UA 版本下限 | 自动跟版（已有） | 同左 |
| 换官方工具 schema | 降质或全灭 | 兜底降质 + 次日自动更新 |
| 新增/删除官方工具名 | 全灭 | 兜底降质 + 次日自动更新 + 告警 |
| 换官方 prompt 措辞 | 全灭 | 次日自动更新 + 告警 |
| 学掉 `mcp_` 前缀 | 全灭，等人改代码 | 诊断梯定位 → 自动换下一档 |
| 新增描述指纹 | 全灭，等人改代码 | 诊断梯定位 → 自动收紧 desc 策略 |
| 换 TLS 指纹 | 全灭，等人抓包改代码 | 资产替换（仍需人工确认） |

TLS 换指纹这一档**做不到全自动**——ClientHello 必须靠抓包，抓包需要人工判断"这是上游真的换了，还是本地环境问题"。但资产化之后，人工只需要"确认 + 替换文件"，不需要重新编译发版。
